# OPC 统一后端架构设计 V1

更新日期：2026-06-15  
状态：架构基线，后续所有项目后端实现应遵守

## 1. 目标

构建一个统一的 Go 后端，服务多个项目，而不是为单个前端页面单独创建多个小后端。

统一后端的目标：
- 支撑多个业务项目共用同一套账号、组织、权限、通知、配置、文件、审计能力
- 支撑多个前端项目分别接入
- 统一部署、统一监控、统一配置管理
- 保证新增项目时不重复造基础设施

## 2. 架构定位

这个后端不是“成绩平台专属后端”，而是：

**OPC 平台统一业务后端**

成绩洞察平台只是它当前的第一个大型业务域。

未来可继续接入：
- 成绩洞察
- 教学诊断
- 家校协同
- 其他学校业务工具

## 3. 设计原则

### 3.1 单后端，多业务域
- 一个部署单元
- 一个 API 服务
- 多个业务模块
- 模块边界清晰

### 3.2 平台能力与业务能力分离

平台公共能力不应散落到各业务模块中，必须独立：
- 用户与身份
- 组织与租户
- 权限与角色
- 文件管理
- 消息通知
- 配置中心
- 审计日志

业务能力独立建模：
- 成绩管理
- 考试分析
- 预警规则
- 展示策略

### 3.3 API 面向前端项目，而不是面向页面
- 前端可以是教师端 Web、小程序、后续家长端或学生端
- API 应按业务能力组织，不按页面组织

### 3.4 多租户优先
- 学校是一级租户
- 所有核心业务数据必须天然带 `school_id`
- 公共能力也要支持租户隔离

### 3.5 渐进式模块化
- 先单体模块化
- 后续若需要，再按领域拆成独立服务
- 当前阶段不建议一开始做微服务

## 4. 统一后端建议分层

## 4.1 接入层
- HTTP API
- 鉴权中间件
- 请求校验
- 统一错误响应
- OpenAPI 文档

建议目录：
- `internal/httpapi`

## 4.2 应用层
- 业务用例编排
- 事务边界
- 调用领域服务
- 调用仓储接口

建议目录：
- `internal/application`

## 4.3 领域层
- 业务规则
- 领域模型
- 领域服务
- 核心约束

建议目录：
- `internal/domain`

## 4.4 基础设施层
- MySQL
- Redis
- 文件存储
- 消息通道
- 日志
- ORM / SQL

建议目录：
- `internal/infrastructure`

## 4.5 平台能力层
- 用户
- 组织
- 权限
- 通知
- 文件
- 配置
- 审计

建议目录：
- `internal/platform`

## 7. 部署方式

统一后端采用单服务部署：
- 一个 Docker 镜像
- 一个环境一份配置
- 一个数据库实例

前端项目分别接同一 API。

优点：
- 部署简单
- 运维成本低
- 公共能力统一
- 多项目共享一套后端逻辑

## 8. 对前端的影响

前端不能再内嵌业务规则，后续应逐步迁移：
- 文件解析逻辑
- 成绩导入校验
- 选课阶段规则
- 学科覆盖校验
- 成绩聚合与重算

前端应只保留：
- 页面
- 表单
- 交互状态
- API 调用

## 9. 近期实施建议

先不急着把所有模块都写完，建议按这条线推进：

### 第一阶段
- 搭统一后端骨架
- 完成平台基础模块占位
- 实现健康检查和基础 API

### 第二阶段
- 先实现成绩业务域
- 先实现考试与成绩导入
- 教师端优先切到接口驱动

### 第三阶段
- 再补分析域、预警域、通知域

## 10. 当前结论

统一后端是合理方向，且当前仓库应按这个方向继续推进：
- 一个 Go 后端
- 多个前端项目接入
- 平台能力和业务能力分层
- 先单体模块化，后续再考虑拆分
